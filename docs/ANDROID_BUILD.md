# Android build (native targets)

**Status: an installable APK exists and runs on real hardware.** Built locally with Gradle on
10 Nov 2026 — `dist/idukaa-1.0.6-android-release.apk` (48,768,604 bytes, SHA-256
`8eb64b7f1b28d9f0d42010d3d88ffd5fb68b933875e88d9f6e652e8fd47060c6`, `versionCode 7`). It was
installed over 1.0.5 on the Infinix X657 with `firstInstallTime` unchanged, so the existing session,
SQLite catalogue and outbox survived. The launcher name is **Idukaa**. `android/` is generated by
`expo prebuild` and git-ignored, so the artifact is not committed; see `docs/CROSS_PLATFORM.md` for
the full cross-platform report.

**1.0.6 ships the offline download and source-label fixes.** It adds the Settings card that saves
Overview, Inventory, Stock movement, Sales and (where permitted) Financial reports for the current
month and year, and labels a downloaded server snapshot **"Saved copy from the server"** instead of
the incorrect "Calculated locally". Settings now reads the installed version instead of a hard-coded
`v1.0.0`. The version code was raised because an APK with the same code is never offered as an
update.

**1.0.5 adds native PDF/print delivery.** `expo-print` (SDK 58) is bundled into the release and
autolinked into `PackageList.java`; its Android implementation is Kotlin-only, so it adds no new
`.so` to the APK. Reports can now write an A4 PDF/print job from the phone, not only from web.
`verify:apk` passes for both shipped ABIs. Installation and physical print tests on this build were
**not run**: the handset was no longer visible to `adb devices` when the build finished.

**1.0.1 crashed before the first screen on Android 10.** On an Infinix X657 (Infinix Smart 6,
Android 10, `armeabi-v7a` only) the app died in `WorkletsModule` with
`couldn't find DSO to load: libworklets.so`. The file was in the APK; dlopen failed because the
libraries compiled from source were built with NDK 28.2 while the packaged `libc++_shared.so` came
from `react-android-0.88.0-release.aar`, built with NDK 27 — `libworklets.so` referenced
`__cxa_init_primary_exception`, which that older libc++ does not export. Both ABIs were affected, so
every Android device running 1.0.1 was affected, not just 32-bit ones. 1.0.2 builds every native
module with React Native's own NDK (27.1.12297006) and is verified on the phone that crashed.

**1.0.3 fixes an empty catalogue that could not heal by itself.** The pull is incremental against a
cursor saved on the device; if that cursor and the local rows drifted apart, every later pull
answered "nothing changed", so Stock and Sell showed nothing while the web app showed the whole shop.
The engine now detects that shape and re-pulls from scratch, the three affected screens offer
**Reload stock list**, a failed pull is reported instead of looking like an empty shop, and
`verify:apk` refuses a bundle that points at `localhost:3000` (the value in `apps/mobile/.env`, which
would sign in on a laptop but never reach the server from a phone).

**1.0.4 fixes why 1.0.3's repair could never run on this phone.** The product INSERT in the native
store (`applyPull`, `src/database/local.ts`) declared 14 columns but bound only 13 placeholders
(the 14th column, `units_per_selling`, was added with the unit-conversion feature). SQLite rejects
such a statement at prepare time, so **every pull aborted before saving a single product** — the
cursor never advanced, `last_sync` was never written, and Stock kept only rows created locally.
On the Infinix X657 running 1.0.3 the log showed exactly this, once per 30-second pass:

```
W/ReactNativeJS: '[sync] pass failed', { [Error: Error code 1: 13 values for 14 columns]
                   code: 'ERR_INTERNAL_SQLITE_ERROR' }   ← sqlite3_prepare_v2
```

while `/reports/dashboard` and `/reports/inventory` answered normally, the Sync screen read
*"Last sync attempt failed · Last synced: Never"*, Stock listed **1** product (created on the phone)
and the server reported **5**. The browser uses the IndexedDB object adapter, which contains no SQL,
so the web app showed the complete catalogue — the exact web/native divergence reported.

The fix binds the missing placeholder, reports a device write failure as its own `storage` code
instead of "the server could not answer", and `tests/catalogue.test.mts` now asserts that **every**
INSERT in `local.ts` binds as many values as it declares columns, so the class of defect cannot
return unnoticed.

A second failure sat behind the first. The production API runs on Render's free tier, where a
sleeping instance took **32.9 s** to answer its first request (measured from this machine on
8 Nov 2026, then 0.5 s once warm), while the client aborted every request after 20 s. The phone was
online and validated the whole time; the pass simply gave up and reported "no internet connection".
Sync push and pull now use `SYNC_TIMEOUT_MS` (60 s, `src/services/api.ts`), which is safe because a
failed pass is retried while a pass cut off mid-download is not; screen requests keep the 20 s
default and the token refresh keeps its 30 s.

## 1. What can be built

| Target | Supported? | How |
|---|---|---|
| **Android APK** (sideload / internal testing) | **Yes — built** | Gradle `assembleRelease` (below), or `eas build --profile preview` |
| **Android AAB** (Google Play) | Yes | Gradle `bundleRelease`, or `eas build --profile production` (`buildType: "app-bundle"`, `autoIncrement`) |
| **iOS IPA** | Configured, not built | `docs/IOS_BUILD.md` |
| **Web / PWA** | **Yes — built** | `npx expo export --platform web` |

## 2. Build it locally (no Expo account needed)

The native settings live in `apps/mobile/plugins/with-android-build-settings.js` (registered in
`app.json`): `compileSdk 37` (required by React Native 0.88 / Expo SDK 58 AAR metadata),
`targetSdk 36`, `buildTools 36.1.0`, `ndkVersion 27.1.12297006` — the NDK React Native 0.88 itself declares, which
`react-android`'s prebuilt `libc++_shared.so` was compiled with. Do not raise it on its own: every
module built from source links against that C++ runtime. Regenerate the native folder first
if it is missing or stale, then build:

```bash
cd apps/mobile
npx expo prebuild --platform android --clean      # only if android/ is absent or out of date

cd android
export JAVA_HOME='C:\Program Files\Java\jdk-17'
export ANDROID_HOME="$LOCALAPPDATA/Android/Sdk"
export EXPO_PUBLIC_API_URL='https://idukaa-qqk2.onrender.com'   # baked into the JS bundle
export IDUKAA_CXX_STAGING='C:/x'                  # Windows only, see below
./gradlew assembleRelease --no-daemon
```

Output: `android/app/build/outputs/apk/release/app-release.apk` (≈7 min once warm, longer cold).
Add `-PreactNativeArchitectures=armeabi-v7a,arm64-v8a` to skip the two x86 ABIs an
emulator-only build needs; that halves the build time and the artifact size.

**Windows / `MAX_PATH`:** CMake mirrors `node_modules` source paths under `android/app/.cxx`, which
overflows the 260-character limit and makes `ninja` fail with
`mkdir(...): No such file or directory`. `LongPathsEnabled` is `0` on this machine, so the fix is a
short staging directory — hence `IDUKAA_CXX_STAGING='C:/x'`. It is only read when set, so Linux/macOS
builds and EAS are unaffected.

Staging alone is not enough for a checkout whose own path is long (this one is ~100 characters): the
object filenames of `react-native-reanimated` still exceeded 260. Build from a short path instead —
copy (or hardlink) the checkout to `C:\b`, keep `node_modules` linked rather than duplicated, and
recreate the workspace links inside it (`mklink /J C:\b\node_modules\@sms\shared C:\b\packages\shared`)
so Metro can resolve `@sms/shared`. `expo prebuild` and Gradle then run entirely under `C:\b`.

### Native compatibility check (run this before every release)

```bash
npm run verify:apk -- dist/idukaa-1.0.6-android-release.apk
```

`scripts/verify-android-apk.mjs` opens the APK, and for **each ABI it ships** checks that every
required library is present (`libworklets.so`, `libc++_shared.so`, `libreactnative.so`, …), that every
`DT_NEEDED` entry is packaged or is a platform library, and that every undefined symbol is exported by
a packaged library or by the platform — using the NDK's own `llvm-nm` and platform stubs. It also
fails a bundle that points at `http://localhost:3000` (`apps/mobile/.env`'s development value): such a
build signs in on a laptop but can never reach the server from a phone, which shows up as an empty
catalogue and no syncing rather than as an error. This is what
catches the 1.0.1 defect class: the run against 1.0.1 fails with
`libworklets.so references … __cxa_init_primary_exception`, and the 1.0.2 build passes. A build should
be considered shippable only when this exits 0.

Install on a phone: `adb install -r dist/idukaa-1.0.6-android-release.apk`, or copy the file across
and open it with "install unknown apps" allowed.

> **The APK is debug-signed.** It installs and runs, but it is **not** publishable and must not be
> distributed to users: Google Play requires a release key, and a later build signed with a
> different key is treated as a different app. Before real distribution, create a release keystore
> (`eas build` does it automatically, or `keytool` + `signingConfigs`) and rebuild.

## 4. Packaging via EAS (optional, needs your Expo account)

```bash
npm i -g eas-cli
eas login
cd apps/mobile
eas init                                    # writes extra.eas.projectId into app.json
eas env:create EXPO_PUBLIC_API_URL=https://idukaa-qqk2.onrender.com --environment production
eas build --profile preview    --platform android     # APK -> internal distribution link
eas build --profile production --platform android     # AAB -> Google Play
```

`eas build` keeps the upload keystore in EAS (**Manage credentials → Android**); back up the
keystore and its password, otherwise users can never receive an update of the same app.
`.gitignore` excludes `*.keystore`, `*.jks`, `*.p12`, `*.pem` and `*.key`.

## 5. Windows

**The web app running on Windows is not a Windows application.** Expo SDK 58 / React Native 0.88 has
no Windows target and `react-native-windows` does not support this version. The supported story is
the installable PWA (Chrome/Edge → **Install app**), which works offline via the service worker —
see `docs/DEPLOYMENT.md`. A Tauri/Electron shell around the web export is a possible future task.

## 6. SQLite and offline on each target

| Target | Local store | Outbox/queue | Notes |
|---|---|---|---|
| Android (native) | **expo-sqlite** (`src/database/local.ts`) | same `enqueue`/`applyResults`/`markRetry` logic | Writes are durable in SQLite before the UI reports success; survives app kill/restart |
| Web / Windows PWA | **IndexedDB** (`src/database/local.web.ts`) | same API, one atomic record per mutation | Durable across reloads; clearing site data deletes unsynced work |

No offline changes were needed for Android: the queue, backoff, idempotency (`op_id`), conflict
handling and shop-scoped `bindShop()` cache wipe are platform-independent.

## 7. Install and update story

- **Internal testing (APK):** install the file above; each new build with the same
  `applicationId` (`rw.shop.management`) and a higher `versionCode` replaces the previous install.
- **Google Play (AAB):** upload to an internal/closed testing track; Play handles delivery and
  staged rollouts. `autoIncrement` raises `versionCode` per build.
- **In-app updates:** the app asks `GET /app/version` (see `docs/DEPLOYMENT.md` for the `APP_*`
  variables) at start, when it returns to the foreground and when connectivity returns — throttled to
  once every 6 hours — and on demand from **More → Check for updates**. If the installed
  `versionCode`/version is behind the published minimum it shows an unmissable banner that opens the
  download URL; the queue and local database are untouched by the upgrade. **EAS Update/OTA is not
  configured** (no `runtimeVersion`/`updates` channel), because `expo-updates` is not installed: every
  change, JavaScript included, needs a new APK. The manifest says so (`ota.enabled: false`) instead of
  implying that a download could replace native code.
- **Environment:** `EXPO_PUBLIC_API_URL` is compiled into the bundle, so the app must be rebuilt
  when the API URL changes.
